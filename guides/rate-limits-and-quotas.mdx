Every API on the Developer Portal enforces two complementary controls on how much you can call it: rate limits and quotas. Understanding the difference between them — and writing code that respects both — is one of the most important steps toward building a stable, production-ready integration. Ignoring limit signals is the single most common cause of self-inflicted outages, where a buggy retry loop floods the gateway and blocks all of an application's traffic. This guide explains how each mechanism works, how to read the headers the API returns, and how to implement a resilient retry strategy.

## Rate Limits vs. Quotas

These two controls operate on different time horizons and serve different purposes:

| | Rate Limit | Quota |
|---|---|---|
| **Time window** | Short (per minute or per second) | Long (per month) |
| **Purpose** | Protect gateway stability; prevent burst traffic | Control total consumption; align with plan pricing |
| **When exceeded** | HTTP `429 Too Many Requests` | HTTP `403 Forbidden` with error code `QUOTA_EXCEEDED` |
| **Resets** | Automatically, at the next window boundary | Monthly, on your billing cycle date |
| **How to resolve** | Wait and retry | Upgrade your plan or wait for next billing cycle |

Think of a rate limit as a flow valve — it controls how fast you can send requests in any short burst. Think of a quota as a fuel tank — it controls how many total requests you get per month.

## Rate Limit Headers

Every API response includes three standard headers that tell you exactly where you stand relative to your rate limit:

| Header | Type | Description |
|--------|------|-------------|
| `X-RateLimit-Limit` | integer | Maximum requests allowed in the current window |
| `X-RateLimit-Remaining` | integer | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp | When the current window resets (UTC) |

Read these headers proactively — do not wait for a `429` to discover that you are close to your limit.

```javascript JavaScript
const response = await fetch("https://api.example.com/v1/catalog", {
  headers: {
    "Authorization": "Bearer YOUR_API_KEY",
  },
});

const limit     = parseInt(response.headers.get("X-RateLimit-Limit"), 10);
const remaining = parseInt(response.headers.get("X-RateLimit-Remaining"), 10);
const reset     = parseInt(response.headers.get("X-RateLimit-Reset"), 10);

const resetDate = new Date(reset * 1000);

console.log(`Limit: ${limit}`);
console.log(`Remaining: ${remaining}`);
console.log(`Resets at: ${resetDate.toISOString()}`);

if (remaining < 10) {
  console.warn("Approaching rate limit — consider slowing request cadence.");
}
```

## Plan Tiers and Rate Limits

Your rate limit depends on your subscription plan. The table below shows the default limits for each tier. Limits apply per API key per minute.

| Plan | Rate Limit | Monthly Quota |
|------|------------|---------------|
| **Free** | 100 req / min | 10,000 req / month |
| **Basic** | 500 req / min | 100,000 req / month |
| **Pro** | 2,000 req / min | 1,000,000 req / month |
| **Enterprise** | Custom | Custom |

<Info>
  Some APIs have lower limits than the plan defaults based on the complexity or cost of the underlying service. Check the API's details page in the catalog for any API-specific overrides.
</Info>

## When You Hit a Rate Limit

When you exceed your rate limit, the API returns:

- **HTTP status**: `429 Too Many Requests`
- **Header**: `Retry-After: <seconds>` — the number of seconds to wait before retrying
- **Body**:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "You have exceeded the rate limit for this API. Retry after the specified delay.",
    "retryAfter": 12
  }
}
```

<Warning>
  Never ignore a `429` response. Retrying immediately without a delay will result in continued `429` responses and will not advance your request. Sustained hammering can trigger a temporary IP-level block that lasts longer than the original rate limit window.
</Warning>

## Exponential Backoff with Jitter

The correct way to handle `429` responses is **exponential backoff with jitter**: wait progressively longer between retries, and add a random offset to prevent multiple clients from retrying in lockstep (the "thundering herd" problem).

```javascript JavaScript
async function fetchWithBackoff(url, options, maxRetries = 5) {
  const BASE_DELAY_MS = 500;
  const MAX_DELAY_MS  = 30_000;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      return response; // Success or a non-retryable error
    }

    if (attempt === maxRetries) {
      throw new Error(`Max retries reached. Last status: ${response.status}`);
    }

    // Honour the Retry-After header if present, otherwise use exponential backoff
    const retryAfterHeader = response.headers.get("Retry-After");
    const retryAfterMs = retryAfterHeader
      ? parseInt(retryAfterHeader, 10) * 1000
      : Math.min(BASE_DELAY_MS * Math.pow(2, attempt), MAX_DELAY_MS);

    // Add jitter: ±20% of the calculated delay
    const jitter = retryAfterMs * 0.2 * (Math.random() * 2 - 1);
    const delay  = Math.round(retryAfterMs + jitter);

    console.warn(`Rate limited. Retrying in ${delay}ms (attempt ${attempt + 1}/${maxRetries})`);
    await new Promise((resolve) => setTimeout(resolve, delay));
  }
}

// Usage
const response = await fetchWithBackoff("https://api.example.com/v1/catalog", {
  headers: { "Authorization": "Bearer YOUR_API_KEY" },
});
const data = await response.json();
```

## Additional Best Practices

Beyond backoff, adopt these habits to reduce how often you hit limits in the first place:

- **Cache responses** — If you call the same read-only endpoint repeatedly with the same parameters, cache the response client-side for an appropriate TTL. A catalog or configuration endpoint rarely changes by the second.
- **Batch requests where the API supports it** — Sending one request with 50 IDs is far more efficient than 50 individual requests.
- **Distribute traffic evenly** — Avoid thundering-herd patterns in your own architecture. If you have a cron job that fires at the top of every hour, add a small random startup delay so all instances do not spike simultaneously.
- **Monitor `X-RateLimit-Remaining`** — Build rate-limit awareness into your client so it slows down proactively, rather than waiting for a `429`.

## Quota Exhaustion

When you have consumed your entire monthly quota, the API returns:

- **HTTP status**: `403 Forbidden`
- **Body**:

```json
{
  "error": {
    "code": "QUOTA_EXCEEDED",
    "message": "Your monthly quota for this API has been exhausted. Upgrade your plan to restore access.",
    "quotaResetDate": "2024-02-01T00:00:00Z"
  }
}
```

Unlike a rate limit, a quota exhaustion does not resolve on its own within minutes. You have two options:

1. **Upgrade your plan** — Go to **Account → Subscriptions**, open the affected subscription, click **Change Plan**, and select a higher tier. Access is restored immediately after the upgrade is confirmed.
2. **Wait for the next billing cycle** — Your quota resets automatically on the date shown in `quotaResetDate`. If your use case is not time-sensitive, this may be the right choice.

<Tip>
  Set up a usage alert at 80% of your monthly quota so you have time to upgrade before access is interrupted. See the [Monitoring Usage](/guides/monitoring-usage) guide for instructions.
</Tip>
