Every request you make to the Developer Portal API must be authenticated using an API key. Keys are generated from your developer account settings and act as both your identity and your permission boundary — they tell the API who you are and which resources you are allowed to access. There are no session cookies or OAuth flows for server-to-server calls; a valid key in the `Authorization` header is all you need.

## Passing Your API Key

Include your API key as a Bearer token in the `Authorization` header on every request:

```http
Authorization: Bearer YOUR_API_KEY
```

Replace `YOUR_API_KEY` with the key you copied from your portal account. The header name and the `Bearer` prefix are both required — omitting either causes a `401 UNAUTHORIZED` response.

## Code Examples

<CodeGroup>

```bash cURL
curl --request GET \
  --url https://api.example.com/v1/catalog/apis \
  --header "Authorization: Bearer YOUR_API_KEY" \
  --header "Accept: application/json"
```

```javascript JavaScript
const response = await fetch("https://api.example.com/v1/catalog/apis", {
  method: "GET",
  headers: {
    Authorization: "Bearer YOUR_API_KEY",
    Accept: "application/json",
  },
});

const data = await response.json();
console.log(data);
```

```python Python
import requests

url = "https://api.example.com/v1/catalog/apis"
headers = {
    "Authorization": "Bearer YOUR_API_KEY",
    "Accept": "application/json",
}

response = requests.get(url, headers=headers)
data = response.json()
print(data)
```

</CodeGroup>

## Troubleshooting a 401 Unauthorized

If any request returns `401 UNAUTHORIZED`, work through the following checks:

<Steps>
  <Step title="Confirm the key exists">
    Open your portal account settings and verify the key you are using is listed. If you deleted or rotated the key, generate a new one.
  </Step>
  <Step title="Check that the key is active">
    Keys can be manually disabled from the dashboard. Look for an "Active" status indicator next to the key. Re-enable it if it has been paused.
  </Step>
  <Step title="Verify the header format">
    Make sure the header reads exactly `Authorization: Bearer YOUR_API_KEY` — with a capital `B` in `Bearer`, a single space between `Bearer` and the key, and no extra characters or whitespace around the key value.
  </Step>
  <Step title="Check for environment mismatches">
    Test keys (prefixed `test_`) only work against sandbox environments, and live keys only work in production. Ensure you're hitting the right base URL with the matching key type.
  </Step>
</Steps>

## API Key Scopes and 403 Forbidden

API keys are scoped to the specific APIs your account is subscribed to. Successfully authenticating (no `401`) does not guarantee access to every endpoint — if you call an endpoint for an API you haven't subscribed to, the server returns `403 FORBIDDEN`.

<Warning>
  A `403` response does **not** mean your key is invalid. It means your key is valid but lacks permission for that resource. Subscribe to the API through the portal, then retry your request.
</Warning>

Key scopes are evaluated at request time, so as soon as your subscription is active you can make calls without regenerating your key.

## Rate Limits and Quotas

Rate limits and usage quotas are enforced per API key. Each subscribed API defines its own rate limit tier (requests per minute) and monthly quota. When you exceed a rate limit, the API returns `429 TOO_MANY_REQUESTS` along with a `Retry-After` header indicating how many seconds to wait before retrying.

<Tip>
  Monitor your usage proactively from the portal dashboard or via the [Usage Metering endpoints](/api-reference/endpoints/usage) to avoid unexpected `429` or `403` quota errors in production.
</Tip>

You can inspect your current rate limit status using the response headers returned on every successful request:

| Header | Description |
|---|---|
| `X-RateLimit-Limit` | Maximum requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp when the window resets |
